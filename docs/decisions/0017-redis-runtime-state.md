# ADR-0017：Redis 仅承载短期运行态

- 状态：已接受
- 日期：2026-08-07

## 背景

PaperLeaf 的 API 可以水平扩展，但进程内限流在多副本之间不一致。问答提交还需要正确处理浏览器重试，不能让同一个幂等请求重复消耗额度。与此同时，用户、任务、消息和 Agent 事件必须支持重启恢复，不能依赖易失缓存。

## 决定

引入 Redis 作为短期运行态存储，首个用途为 Agent 提交限流：

- 使用 Lua 原子完成计数、TTL 和幂等判定；
- 按用户隔离，Key 中只保留标识摘要；
- 相同幂等键复用首次判定；
- Redis 故障时降级为当前 API 进程内计数；
- PostgreSQL 继续保存消息、Run、作业、事件和 Checkpoint；
- Redis 不启用持久化，也不进入业务备份恢复协议。

## 未选择的方案

- 只用进程内字典：实现简单，但多 API 副本配额不一致。
- 把限流计数写入 PostgreSQL：一致性明确，但高频短期写会与业务事务争用。
- 把会话或 Agent 事件迁入 Redis：会削弱当前重启恢复和审计能力，不符合真相源边界。

## 影响

Redis 重启会重置短期限流窗口，这是可接受的；Redis 故障期间单节点仍有限流保护，但多个 API 副本之间暂时不共享额度，因此必须通过健康状态和后续监控暴露降级。
