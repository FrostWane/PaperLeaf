# ADR-0018：持久 RAG 摘要与低基数时序指标并存

## 状态

已接受，2026-08-07。

## 决策

- 每个终态 Agent Run 在 PostgreSQL 的 `result_summary.rag_trace` 中保存内容无关的 V1 运行摘要；
- 管理员页面从持久摘要聚合 24 小时、7 天和 30 天质量视图；
- API 与 Worker 同时暴露 Prometheus 指标，用 Grafana 查看趋势和进程资源；
- Trace 和指标只使用受控枚举、数量与耗时，不保存问题、证据、回答或业务标识；
- 意图分类采用确定性规则，不为可观测性额外调用 LLM；
- PostgreSQL 是可审计统计的事实源，Prometheus 是可重置的时序观测层。

## 原因

仅使用 Prometheus 会在进程重启后丢失历史，也难以补算旧运行；只扫描数据库又不适合高频时序趋势和进程资源。双层设计让本地管理员能看到可解释的 RAG 漏斗，同时保留标准监控工具的扩展路径。

## 未选择

- 把问题、Chunk 或 Run ID 写入 Prometheus Label：会造成高基数和隐私风险；
- 为意图分类增加一次模型调用：增加费用、延迟和不可复现性；
- 立即引入完整 OpenTelemetry Collector：当前单机闭环尚未证明需要这层复杂度；
- 把运行摘要写入 Redis：Redis 可丢失，不符合审计和跨重启统计要求。

## 后果

新增运行会获得完整 RAG Trace；升级前的记录仍进入运行总数和失败总数，但没有细分通道、意图与阶段耗时，因此管理员页面必须展示指标覆盖率。数据规模超过单次 5000 条聚合上限后，需要按小时预聚合，而不是无限扩大管理接口查询。
